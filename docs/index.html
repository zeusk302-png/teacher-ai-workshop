RAG와 NotebookLM

검색·생성의 원리와 직접 구축에 필요한 자원을 살펴봅니다. 각 탭의 ‘심화 설명’에는 강의에서 풀어 설명할 내용을 담았습니다.

왜 필요한가

데이터가 필요한 이유

자료를 연결하지 않은 AI 답변에는 학교별 규정이나 적용 연도가 빠질 수 있습니다.

같은 질문

“수행평가에 결시한 학생의 추가 평가 원칙을 정리해 줘.”

자료 없이 질문

어느 학교·어느 학년도의 규정인지 알려주지 않았습니다. 일반적인 설명이 나오더라도 우리 학교에 적용되는지 확인하기 어렵습니다.

자료를 검색해 질문

학교규정집과 적용 지침에서 질문에 맞는 내용을 찾고, 검색한 내용을 활용해 답변을 구성할 수 있습니다. RAG는 이처럼 검색한 내용을 AI 입력에 함께 제공하는 방식입니다.

RAG는 Retrieval-Augmented Generation의 줄임말입니다. 질문에 관련된 자료를 검색해 AI에 맥락으로 제공하고, 이를 활용해 답변을 생성하는 방식입니다.

개념 출처: NIST RAG 정의 · 위 질문과 두 상황은 연수용 예시이며 실제 규정 답변이 아닙니다.

심화 설명자료를 읽히는 것과 학습시키는 것

모델의 지식과 이번 업무의 사실

언어 모델은 학습 과정에서 익힌 패턴으로 문장을 만듭니다. 학교 이름을 알고 있다고 해서 그 학교의 최신 규정, 이번 행사 일정, 담당자의 결정을 모두 알고 있는 것은 아닙니다. 업무 문서에는 일반적인 설명보다 이번 업무에 맞는 자료와 입력값이 필요합니다.

예를 들어 사전답사 계획서를 작성할 때 지침에서 찾을 것은 서식의 항목과 점검 사항입니다. 이번 날짜·장소·답사자는 담당자가 제공할 사실입니다. 예시 문서에 적힌 지난해 날짜와 이름은 작성 방식을 참고할 자료이지 이번 계획의 입력값이 아닙니다.

프롬프트·RAG·추가 학습의 차이

프롬프트는 지금 해야 할 일을 전달하는 입력입니다. RAG는 질문에 맞는 자료를 검색하고 그 결과를 모델 입력에 보태는 구성 방식입니다. 파인튜닝은 별도의 학습 과정으로 모델의 매개변수를 조정하는 작업입니다. 세 가지는 같은 뜻이 아니며 함께 사용할 수도 있습니다.

규정이 개정됐을 때 RAG에서는 검색 대상 자료와 색인을 갱신하는 접근을 취할 수 있습니다. 자료를 업로드하거나 긴 지시문을 썼다는 사실만으로 모델이 재학습됐거나 다음 대화에서도 그 내용을 기억한다고 판단하지 않습니다.

파일 첨부가 곧 RAG라는 뜻은 아닙니다

파일 내용을 한 번에 입력에 넣을 수도 있고, 일부 구간을 검색해 넣을 수도 있습니다. 파일을 첨부했다는 화면만 보고 내부에 어떤 검색 절차가 있는지 단정할 수는 없습니다. 우리에게 필요한 것은 업무에 맞는 내용을 실제로 찾았는지 확인할 수 있는 작업 방식입니다.

이 연수에서는 NotebookLM의 소스 선택과 인용 확인 기능을 사용합니다. 외부 AI에는 확인한 발췌문과 양식을 사람이 전달합니다. 외부 AI가 원래 노트북 전체에 접속해 질문마다 다시 검색하는 연결은 만들지 않습니다.

문서를 완성하려면 세 종류를 구분합니다

첫째, 지침·규정은 적용할 내용을 정하는 자료입니다. 둘째, 기존 작성 예시는 표현과 구성의 참고 자료입니다. 셋째, 빈 양식은 제목·항목·표·결재란 등 결과물의 구조입니다. 자료를 모을 때부터 이 역할을 구분하면 예시의 사실을 잘못 복사하는 일을 줄일 수 있습니다.

여기에 이번 업무의 확정 입력값을 별도로 적습니다. 자료가 알려주는 내용, 사람이 결정한 내용, 아직 결정되지 않은 내용을 나누어 두면 어느 항목을 검색하고 어느 항목을 질문해야 하는지가 분명해집니다.

참고: RAG 정의 · NIST · RAG 원 논문 · Lewis 외, 2020 · 학교 업무 예시와 진행 방식은 연수용으로 구성했습니다.

자료를 넣는 것과 모델을 추가 학습시키는 것은 다른가요?

RAG의 핵심은 답변할 때 관련 자료를 찾아 제공하는 데 있습니다. 자료를 등록했다는 이유만으로 모델 자체가 다시 학습되거나 내용을 영구히 기억한다고 볼 수는 없습니다.

심화 설명검색 품질은 어디에서 달라지는가

검색 전에 문서를 읽을 수 있어야 합니다

PDF에 글자가 보이더라도 컴퓨터가 읽을 수 있는 텍스트가 들어 있는지는 다릅니다. 스캔한 문서는 OCR로 글자를 추출해야 할 수 있습니다. 표에서는 열 제목과 셀의 관계가 깨지기도 하므로 검색 결과를 원본 화면과 대조합니다.

직접 구축할 때는 긴 문서를 검색하기 좋은 구간으로 나눕니다. 이를 청크라고 합니다. 너무 짧게 자르면 조건과 예외가 떨어지고, 너무 길면 관계없는 내용까지 섞입니다. 조항·제목·표 구조를 고려하고 자료명·쪽·버전 같은 메타데이터를 함께 보관합니다.

키워드 검색과 의미 검색

키워드 검색은 문서에 실제로 있는 단어를 찾는 데 유용합니다. 서식 번호, 문서 제목, 고유한 업무 용어처럼 정확한 표현을 아는 경우 먼저 사용하기 좋습니다. 의미 검색은 질문과 문서의 표현이 달라도 관련 내용을 찾도록 설계하는 방식입니다.

임베딩은 텍스트 등을 숫자 벡터로 표현하는 방법입니다. 벡터 간 유사도를 검색에 사용할 수 있지만, 유사하다는 사실이 최신 규정이거나 옳은 답이라는 뜻은 아닙니다. 키워드와 벡터 검색을 함께 쓰는 하이브리드 방식도 있습니다. 이 설명은 일반적인 검색 설계이며 NotebookLM 내부 구조를 설명한 것은 아닙니다.

질문은 결과물부터 거꾸로 나눕니다

‘계획서 만들어 줘’부터 시작하면 필요한 자료와 형식이 섞입니다. 먼저 ‘사전답사 계획서의 필수 항목과 서식 위치를 찾아 줘’, 다음으로 ‘점검 사항과 적용 조건을 정리해 줘’처럼 찾을 대상을 나눕니다. 그 뒤 이번 일정과 인원을 주고 작성 요청으로 묶습니다.

이 연수의 검색 최적화는 자료 선별, 정확한 문서명·업무 용어 사용, 학교급·시점 명시, 질문 분리, 원문 확인의 반복입니다. 찾지 못하면 동의어를 바꾸거나 검색 범위를 조정합니다. 같은 질문을 되풀이하기 전에 자료가 등록·선택됐는지부터 확인합니다.

관련 원문을 충분히, 불필요한 자료는 줄여서

모델이 한 번에 처리하는 입력에는 한계가 있습니다. 관련 없는 자료를 길게 붙인다고 필요한 조건을 더 잘 찾는다고 보장할 수는 없습니다. 긴 입력에서 정보 위치에 따라 성능이 달라진 연구도 있지만, 이를 모든 최신 모델의 동일한 실패로 일반화하지는 않습니다.

작성에 필요한 구절은 조건·예외·표 제목이 끊기지 않게 전달합니다. 요약만 보내면 중요한 제한이 사라질 수 있고, 인용 번호만 보내면 원문이 전달되지 않을 수 있습니다. ‘어느 자료의 어느 부분인지’와 ‘실제로 사용할 문장’을 함께 남깁니다.

참고: 문서 분할 · Microsoft · 벡터 검색 · Microsoft · 긴 입력의 정보 활용 연구 · Liu 외, 2023 · 학교 업무 예시와 진행 방식은 연수용으로 구성했습니다.

모델 API를 사용하면 모델을 실행할 GPU를 직접 갖추지 않아도 됩니다. 검색도 키워드 방식으로 구성할 수 있으며, 의미 검색을 선택할 때 임베딩과 벡터 검색 기능이 필요합니다. 별도 벡터 데이터베이스가 모든 RAG의 필수 조건은 아닙니다. 규모와 선택한 모델·검색 방식에 따라 필요한 자원이 달라집니다.

RAG와 NotebookLM은 어떤 관계인가요?

RAG는 검색한 내용을 생성 모델의 입력에 제공하는 설계 방식입니다. NotebookLM은 자료 등록·검색·정리 기능을 제공하는 제품입니다. 자료를 등록했다고 모델을 다시 학습한 것은 아니며, NotebookLM 실습을 자체 RAG 시스템 개발과 동일하게 설명하지 않습니다.

출처: NIST RAG 정의 · Microsoft RAG 구성·검색·운영 안내. NotebookLM의 내부 검색 알고리즘을 단정하는 설명은 아닙니다.

심화 설명직접 구축할 때의 개발과 운영

자료 준비와 질문 처리는 별도 흐름입니다

자료 준비에서는 문서를 수집하고 텍스트를 추출한 뒤 구간을 나누고 검색 색인을 만듭니다. 질문이 들어오면 관련 구간을 검색하고, 질문·원문·지시문을 묶어 생성 모델에 전달합니다. 결과에는 원문을 다시 찾아갈 수 있는 자료 식별 정보를 남깁니다.

이 두 흐름을 연결하려면 파일 저장, 검색 기능, 모델 호출, 오류 처리와 화면을 구현할 프로그램이 필요합니다. 파일 생성까지 자동화하려면 문서 라이브러리나 변환 도구, 원본 양식 처리와 생성 파일 검증도 별도로 연결해야 합니다.

필수 자원과 선택 자원을 구분합니다

생성 모델을 API로 호출하면 모델을 돌리는 GPU를 직접 설치하지 않아도 됩니다. 자체 모델을 실행할 경우에는 모델 크기와 처리량에 맞는 메모리·연산 장비가 필요합니다. 어떤 방식을 택하든 프로그램 실행 환경과 자료 저장 공간은 준비해야 합니다.

검색은 키워드 방식으로도 구성할 수 있습니다. 의미 검색을 선택하면 임베딩 생성과 벡터 검색 기능을 준비합니다. 별도 벡터 데이터베이스나 모델 재학습이 모든 RAG에 필수인 것은 아닙니다. 자료량, 동시 사용자, 비용, 보관 조건에 따라 구성을 정합니다.

업무에서는 개정과 권한이 계속 바뀝니다

색인을 한 번 만들고 끝내면 개정 전 자료가 계속 검색될 수 있습니다. 문서의 버전·시행일·담당자를 관리하고, 교체할 때 검색 대상에서도 이전 버전을 처리해야 합니다. 서로 다른 자료가 충돌할 때는 충돌을 드러내고 담당자가 판단할 수 있게 해야 합니다.

여러 사람이 쓰는 시스템은 검색 단계부터 사용자에게 허용된 문서만 반환하도록 설계해야 합니다. 검색 후 화면에서만 숨기는 방식으로는 충분하지 않습니다. 요청 기록을 남길 때도 어떤 자료와 입력값을 기록할지, 누가 볼 수 있을지 정합니다.

2시간 연수에서 준비된 서비스를 쓰는 이유

직접 구축은 가능하지만 개발과 운영을 익히는 데 별도 시간이 필요합니다. 이번 수업은 교사가 실제 양식 문서를 만들고 다음 업무에 재사용하는 데 시간을 씁니다. 자료 검색·인용·요청 정리에 NotebookLM을 쓰고, 파일 작성은 외부 AI의 지원 기능을 이용합니다.

자체 시스템으로 발전시키려면 먼저 반복되는 문서 한 종류, 필요한 자료 범위, 입력 항목, 완료 기준을 정합니다. 수업에서 확인한 수동 흐름을 기준으로 복사·첨부·파일 생성 중 반복 비용이 큰 단계를 차례로 연결합니다. 처음부터 모든 학교 업무를 한 시스템에 담을 필요는 없습니다.

작성 요청에는 항목별로 넣을 내용과 자료명·쪽·원문 발췌, 이번 업무 입력값, 유지할 구조와 검토 기준을 넣습니다. 원문에서 찾지 못한 정보는 빠진 채로 숨기지 말고 [확인 필요]로 남깁니다. 요청을 만든 뒤에도 사람이 발췌와 입력값을 대조합니다.

외부 AI에는 실제로 필요한 것을 전달합니다

검토한 작성 요청과 필요한 원문, 편집할 원본 양식을 한 묶음으로 전달합니다. ‘아까 그 노트북 참고해’라는 말만으로 다른 서비스가 노트북을 읽을 수 있다고 가정하지 않습니다. 이 수업에서 서비스 사이의 복사와 첨부는 사람이 합니다.

파일 작성 기능이 있는 환경에서 항목 입력과 표 작성, 파일 저장을 요청합니다. PDF 양식을 보고 DOCX로 재구성한 결과와 원본 HWPX의 구조·서식을 그대로 유지한 결과는 구분해야 합니다. 계정에서 지원하는 형식과 실제 생성 결과를 확인합니다.

양식과 스킬의 역할

양식은 완성할 문서의 구조입니다. 스킬은 특정 환경에서 반복 작업의 지침과 필요한 자원·도구 사용법을 묶은 것입니다. 문서를 읽고 작성하고 검사하는 순서를 일관되게 적용하는 데 활용할 수 있습니다.

스킬 이름을 프롬프트에 쓰는 것만으로 없는 검색 기능이나 파일 생성 도구가 생기지는 않습니다. 이번 기본 실습에는 별도 스킬 설치가 필요하지 않습니다. 스킬 목록은 반복 작업을 발전시킬 때 참고하며, 실제 설치·실행은 지원 환경과 필요한 권한을 확인한 별도 단계입니다.

사람이 남겨 두는 판단과 검토

어떤 자료가 적용되는지, 이번 입력값이 확정됐는지, 승인받은 표현인지 결정하는 주체는 업무 담당자입니다. AI가 스스로 맞다고 답해도 파일을 열어 본문과 표를 확인합니다. 조건을 바꿨다면 이전 날짜와 인원이 다른 곳에 남았는지도 찾습니다.

제품 기능은 계속 바뀝니다. NotebookLM에도 문서 생성 관련 기능이 추가되고 있으므로 ‘이 제품은 검색만 가능하다’처럼 고정해 설명하지 않습니다. 여기의 역할 분담은 자료 검색과 파일 작성의 책임을 구분해 배우기 위한 수업 구성입니다.

  1. 자료에서 찾을 내용

  3. 작성 조건과 검토 기준

    유지할 항목·표 구조·출력 형식, 미확정 정보 처리, 날짜·시간·총인원 검사 방법을 지정합니다.

    외부 AI에 작성 요청과 필요한 원문, 원본 양식을 함께 전달합니다. NotebookLM의 인용 번호만으로 원문 전체가 전달되지는 않습니다.

심화 설명재사용할 수 있는 작성 요청 설계

업무를 입력·처리·출력으로 적습니다

입력은 확정된 일정·장소·인원·예산과 사용할 자료입니다. 처리는 자료에서 필수 항목을 찾고, 양식에 맞춰 문장을 쓰고, 표와 수치를 대조하는 순서입니다. 출력은 문서 파일과 사람이 확인할 항목입니다. ‘잘 작성해 줘’보다 완료 상태를 구체적으로 정하는 것이 먼저입니다.

사전답사 계획서라면 일시·장소·일정표·답사자·이동수단·점검 사항이 출력에 있어야 합니다. 아직 정하지 않은 이동수단은 [확인 필요]로 남겨야 합니다. 빈칸을 모두 채우는 것과 사실에 맞게 완성하는 것은 다릅니다.

고정 규칙과 바뀌는 값을 분리합니다

고정 규칙에는 제목과 항목 순서, 표 구조, 문체, 미확정 정보 처리, 결과 형식과 검토 절차를 둡니다. 바뀌는 값에는 이번 날짜·시간·장소·답사자·인원처럼 매번 달라지는 정보를 적습니다. 예시를 복사해 조금씩 고치는 방식보다 변경 대상을 찾기 쉽습니다.

입력값은 ‘일시: … / 장소: … / 답사자: … / 인원: …’처럼 항목별로 씁니다. 합계 인원과 명단이 다르거나 일정의 끝이 시작보다 빠르면 생성 전에 질문하도록 요청합니다. 모순을 그럴듯하게 메워 문서로 확정하지 않도록 합니다.

지시·참고 자료·입력값을 구획합니다

작성 순서와 금지 사항은 지시 영역에, 검색한 발췌문은 참고 자료 영역에, 이번 업무의 사실은 입력값 영역에 넣습니다. 기존 문서에 적힌 ‘제출하라’ 같은 문장을 서비스의 실행 명령으로 취급하지 않도록 구분합니다. 구분선은 읽기와 검토를 돕는 수단이며 보안 기능을 보장하지는 않습니다.

출력에는 문서 파일 외에 항목별 반영표와 확인 필요 사항을 요청합니다. 자료명과 쪽을 함께 보관하면 다음 담당자가 어느 문장을 보고 작성했는지 다시 찾을 수 있습니다. 실제 문서에 넣을 내용과 검토용 설명도 나누도록 합니다.

단계를 구분하지 않고 ‘더 정확하게 다시 해 줘’만 반복하면 무엇이 고쳐졌는지 알기 어렵습니다. 검색한 원문, 외부 AI에 실제 보낸 입력, 반환 파일을 비교하면 오류가 생긴 지점을 좁힐 수 있습니다.

완료 기준을 문서 밖에도 남깁니다

검토표에는 필수 항목, 입력값, 원문과 대조할 문장, 확인 필요 사항, 파일 상태를 둡니다. 문서가 생성됐다는 알림은 파일 내부의 값과 서식까지 맞다는 증거가 아닙니다. 내려받은 파일을 열고 표·글꼴·쪽 나눔과 인쇄 화면을 봅니다.

수정할 때는 변경된 값뿐 아니라 이전 값도 검색합니다. 본문은 바뀌었는데 일정표나 머리말은 그대로일 수 있습니다. 명단과 총인원, 날짜와 요일, 합계와 세부 금액처럼 서로 연결된 값도 대조합니다.

정상·누락·충돌·변경 사례로 시험합니다

하나의 정상 사례만 통과하면 정보가 빠진 경우를 놓치기 쉽습니다. 최소한 정보가 모두 있는 사례, 이동수단처럼 미정 항목이 있는 사례, 인원과 명단이 다른 사례, 날짜·인원을 바꾼 사례를 비교해 봅니다. 없는 정보는 확인 필요로 남기고 충돌은 드러내야 합니다.

우선은 통과·수정 필요를 항목별로 기록하면 됩니다. ‘업무 시간이 줄었다’는 효과는 같은 범위의 업무를 실제로 수행한 시간을 비교한 뒤 판단합니다. 이번 연수의 120분은 진행 계획이며 업무 절감 시간을 측정한 결과가 아닙니다.
